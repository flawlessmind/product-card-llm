# Генератор черновика карточки товара

Берёт JSON с данными о приборе, отправляет в локальную LLM (Ollama)
и выдаёт черновик карточки для B2B-магазина в Markdown и JSON.

Для каждого товара формируется:

- SEO-заголовок до 70 символов;
- SEO-описание 800–1200 символов;
- список ключевых характеристик (недостающие помечены «данных нет»);
- 3–5 поисковых запросов;
- блок для менеджера: кому подходит и какие задачи решает;
- блок «Требует внимания» — что нужно уточнить или проверить вручную.

## Установка

Нужны Python 3.10+ и [Ollama](https://ollama.com).

```bash
git clone https://github.com/flawlessmind/product-card-llm
cd card-generator

python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt

ollama pull qwen2.5:7b           
cp .env.example .env             
```

API-ключи не нужны. Настройки (`OLLAMA_HOST`, `OLLAMA_MODEL`, `OLLAMA_TIMEOUT`) читаются из
переменных окружения или из `.env`, который добавлен в `.gitignore`.

## Запуск

```bash
ollama serve                     

python main.py data/product_1.json data/product_2.json
```

Результат печатается в консоль и сохраняется в `output/<имя файла>.md` и `.json`.
Другая папка: `-o my_dir`. Если один из файлов некорректен, остальные всё равно
обрабатываются, а код возврата будет 1.

Тесты (LLM в них подменяется):

```bash
python -m unittest discover -s tests -t .
```

## Формат входных данных

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": { "диапазон измерений": "0–1,6 МПа", "класс точности": "1,5" },
  "description": "Прибор предназначен для..."
}
```

Обязательно только `name` и хотя бы одно из `specs` / `description`.
Всё остальное можно не заполнять — сервис сообщит, чего не хватает.

Примеры входных данных лежат в `data/`. Первый товар взят из примера ТЗ,
второй придуман для проверки.

## Примеры результата

Лежат в `examples/` (получены локальным запуском на указанной в файле модели).

## Промпт и принятые решения

**Промпт** (`cardgen/prompt.py`) состоит из системной инструкции и данных товара в JSON.
В инструкции: роль редактора, запрет использовать любые факты кроме входных,
явное правило «нет данных — пиши «данных нет»», требования к каждому полю и лимиты длины.
Ответ запрашивается строго по JSON-схеме (параметр `format` в Ollama), поэтому парсинг
не зависит от того, как модель решит оформить текст.

**Защита от выдуманных характеристик** — не только промпт, но и код:

1. Список характеристик в карточке собирается кодом из `specs`, модель его не переписывает.
   Отсутствующие стандартные поля (класс точности, питание, степень защиты и т. д.) добавляются
   с пометкой «данных нет» и попадают в предупреждения.
2. После генерации все числа из текста сверяются с числами из входных данных. Незнакомые
   числа выводятся в предупреждении для проверки человеком.
3. Пункты блока для менеджера проверяются по словам: если в них есть слова, которых нет
   во входных данных, это попадает в предупреждения.
4. Пустые пункты блока для менеджера и производитель заменяются на «данных нет».

**Длина.** Маленькие модели плохо считают символы, поэтому длина проверяется в коде.
При нарушении модели отправляется обратная связь с фактической длиной (до 3 попыток).
Если после попыток текст всё ещё длиннее лимита, он обрезается по границе предложения
(это не добавляет фактов) с пометкой в предупреждениях. Слишком короткий текст не дополняется,
а только помечается: при малом объёме данных 800 символов без выдумок не набрать.

**Ошибки.** Невалидный JSON, не-объект, пустое имя, пустые значения в `specs`, недоступный
Ollama, отсутствующая модель, таймаут, невалидный ответ модели — каждый случай даёт понятное
сообщение, без трейсбека.

## Ограничения

- Если во входных данных мало фактов, модель склонна «растягивать» текст оценочными
  фразами. Промпт это запрещает, но полностью гарантировать это нельзя — нужна вычитка.
- Проверка чисел ловит выдуманные цифры, но не выдуманные слова (например, «взрывозащищённый»).
  Текст всё равно должен читать человек.
- Список «ожидаемых» характеристик общий для всех приборов. Для механического манометра
  «питание» будет помечено как «данных нет», хотя ему оно не нужно.
- Только Ollama, без веб-формы.
- При малом объеме входных данных SEO-описание получается короче 800 символов. Это сделано намеренно, чтобы не выдумывать факты, а в карточке остается предупреждение.

## Что можно улучшить

- Свои списки ожидаемых характеристик по типам приборов (давление, температура, расход).
- Проверка и единиц измерения, и значимых терминов, а не только чисел.
- Веб-форма или простой HTTP-эндпоинт (FastAPI) для контент-менеджера.
- Второй проход «LLM-проверяющий», сверяющий каждое утверждение с исходными данными.
- Адаптеры для облачных API (OpenAI, Anthropic) через тот же интерфейс `llm.chat`.
- Загрузка PDF-паспортов с извлечением характеристик.
